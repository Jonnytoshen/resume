**技术栈**：TypeScript、Node.js、飞书开放平台 SDK、MCP SDK、Claude Code / Codex CLI

**背景与方案**：把飞书当作 AI 编程 CLI 的指挥台——一个话题对应一个任务，多个机器人按角色（助理 / 产品 / 开发）组成团队互相 @ 协作，并按 cron 定时巡检，让「发起任务、确认方案、接收结果」都发生在 IM 里。常驻 Node 进程通过飞书长连接接收消息，按话题维护会话并把任务交给 CLI 子进程执行，解析其事件流后实时回写为可交互卡片；同时自建 MCP Server，把「提问、提交方案、派发任务、管理定时任务」四项能力反向暴露给被调用的 CLI，形成人机双向的审批闭环。

- **CLI 适配层**：统一 Claude Code 与 Codex 两套事件协议，抽象出「启动 → 流式事件 → 工具调用 → 结果」的统一时序；支持跨消息续接会话、上下文压缩与 token 统计，切换底层 CLI 不影响上层编排。
- **会话与任务编排**：以话题为任务边界维护会话状态与子进程生命周期，任务可并发推进、可中断续接；子进程异常退出时保留现场，重发消息即可在同一上下文里继续。
- **流式上屏与节流**：工具调用事件实时渲染为任务卡片，按固定间隔节流并串行写入，规避飞书卡片更新频控与并发写入导致的乱序覆盖。
- **反向 MCP 工具**：需求有歧义时由 Agent 主动发卡片确认，方案获批后才进入实现——把审批点前移到写代码之前；派发任务与管理定时任务同样以工具形式交回给 CLI。
- **多角色协作**：配置驱动注册角色、技能与独立工作区，@ 即可交接任务与发起评审，支持多轮往复；角色之间通过共享任务上下文协作，不必人工搬运。
- **定时巡检**：支持 cron 三类规则与运行记录持久化，巡检结果回流到同一会话；配套可注入故障的日志靶场和增量巡检技能，用故障复现验证巡检链路本身是否可靠。

**结果**：交付 v0.1.0–v0.5.0 五个版本，由单 bot 回声演进到多角色团队协作与方案审批闭环，打通「需求澄清 → 方案确认 → 实现 → 代码审查」完整链路；沉淀 7 个 Agent 技能，覆盖需求澄清、方案拆票、实现、代码审查，以及飞书文档与云盘操作。作为日常开发工具使用，任务从终端搬到 IM，离开工位也能发起与跟进，可同时推进多个互不依赖的任务。

#### Super Agent Coding ｜ 从零实现的 TypeScript Agent 运行时 ｜ 独立开发 ｜ 2026.05 – 2026.08

**技术栈**：TypeScript、Node.js、Vercel AI SDK（`streamText` / `fullStream`）、Qwen（DashScope 兼容接口）、MCP、pnpm

**背景与方案**：个人研究型项目，用一个 TypeScript CLI 从零实现 Agent 的工具调用、多步循环与上下文治理（约 4300 行、87 次提交、12 个语义化版本），目的是搞清楚框架里每一步究竟在做什么，而不是调用现成框架。分三层：循环层消费 AI SDK `fullStream` 事件流跑多步推理；工具层由 ToolRegistry 统一管理内置与 MCP 工具，并按元数据调度；上下文层在每轮前后做截断与压缩。

- **Agent Loop 与失控防护**：多步工具调用循环（上限 15 步），叠加三种循环检测（三级阈值先提醒后阻断）、指数退避重试（±25% 抖动）与 Token 预算；Mock 模型让死循环、重试、并发三类问题可复现，回归不依赖真实模型与网络。
- **工具系统与并发调度**：ToolRegistry 统一注册并转换为模型格式，调度策略交由元数据决定——只读工具并行、写工具串行，锁在 `finally` 释放；内置 12 个工具，超长结果按头尾截断，避免单次工具输出吃掉上下文。
- **MCP 接入与延迟加载**：手写 stdio JSON-RPC 客户端接入 GitHub MCP；工具默认延迟加载，prompt 只保留名字与 hint，由 `tool_search` 按需注入 Schema，工具数量增长时 prompt 体积保持可控。
- **上下文压缩与三层防线**：microcompact 按白名单清理旧结果，加上 LLM 结构化摘要（标识符保留、对齐 user 边界、累积旧摘要）；外围再叠加结果截断与 TTL 修剪，75% 占用触发。

**结果**：走通「模型调用 → 工具执行 → 结果回灌 → 继续推理」的完整链路，理解 Agent 的稳定性来自循环控制、工具契约与上下文预算三者共同约束，而非单个 prompt；覆盖内置工具与 MCP 两条接入路径，形成「先控制 prompt 体积、再扩展工具数量」的判断习惯；独立完成 12 个版本的约定式提交 → 自动 CHANGELOG → 语义化发布闭环。

## 个人评价

做技术这件事，比起追新，更在意把事情弄明白：一个方案为什么成立、边界在哪里、什么时候会失效。想不通的时候，倾向于自己动手写一遍验证，而不是先接受一个现成结论。

- **对完整交付有偏好**：从想清楚问题，到实现、验证、再回头修边界，更愿意把一件事跟到能用为止，而不是停在“功能写完”。
- **不太适应“差不多就行”**：会为一处说不清的配置多写一句说明，也会为一个不容易复现的问题多跑几遍；不喜欢用复杂度换观感，够用的方案就到此为止。
- **能忍受不确定**：需求不清楚时愿意先问、先试，攒出方向再动手；一个人做项目时能自己定节奏，在团队里也做得住写规范、看代码、做支持这类不显眼的事。
- **兴趣保持得比较久**：有过连续几个月业余时间写同一个项目的经历，也常写只为弄清原理的小工具；乐意交流，但更相信做出来比说清楚更有说服力。
